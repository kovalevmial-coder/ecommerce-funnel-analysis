# Заметка 03 — Сегментация сессий: фиксированные бизнес-сегменты и воронка по сегментам

> Личная учебная запись (learning note). Этап 03 из 7: нарезка 4,54 млн сессий по пяти
> семействам (цена, новизна визита, выходные, часть суток, месяц) и подсчёт той же
> воронки отдельно по сегментам — всё ещё описательно, без статистических проверок.
> Проект: воронка конверсии интернет-магазина косметики,
> датасет E-commerce Events History (Kaggle, mkechinov), 2019-10 — 2020-02.

---

## Цель этапа

1. **Сегментные метки** — `assign_segments`: пять колонок-меток на сессию (`price_tier`,
   `visit_kind`, `is_weekend`, `daypart`, `month_label`).
2. **Воронка по сегментам** — `segment_funnel`: те же три конверсии, но отдельно для
   каждого сегмента (с размером сегмента `n_sessions` для будущей практической значимости).
3. **Честная картина «кто и какова конверсия»** — описательный разбор перед этапом 05
   (pre-registration), когда эти же сегменты станут группами сравнения.

На выходе — `data/processed/segment_<by>.csv` для каждого семейства, несколько графиков в
`assets/` и описательные числа размеров сегментов.

## Зачем это важно

**Почему фиксированные бизнес-пороги (<5 / 5–30 / 30–150 / 150+ EUR) вместо квантилей?**
Квантильная нарезка («10 % цен») до анализа красиво делит данные поровну, но не имеет
смысла для компании: «низкий прайс» у CVS-сети — это долларовый порог, а не позиция в
гистограмме. Фиксированные границы делают вывод переиспользуемым между датасетами и
соответствуют решению, которое бизнес реально может принять (переставить ли цены через
порог). Цену такой нарезки мы платим открыто: сегменты разного размера (от 42 тыс. до
2,1 млн сессий) — и редкий сегмент потом надо трактовать осторожно.

**Почему здесь ещё нет статистики?** Мы осматриваем размеры и формы — это описательный
этап. Любой «вывод» вроде «budget конвертирует лучше» сейчас был бы подгонкой под
найденный результат (контроль p-hacking). Поэтому этап 05 зафиксирует гипотезы и пороги
ДО того, как итоги сегментов будут предъявлены как значимые.

**Почему «NA» цена не выбрасывается молча?** Сессий без ценовых событий в реальных данных
нет (0 строк с null `median_price`), но контракт `assign_segments` обязан их обработать:
«не знаем цену» — это честная метка, а не дыра в данных. Решение, «исключать ли NA»,
принимается на этапе 05 явным правилом, а не молчаливым дропом.

## Ключевые термины

- **Сегмент (segment)** — подмножество сессий по значению метки из фиксированного
  семейства (например, `price_tier == "luxury"`).
- **Ценовой ярус (price tier)** — фиксированные границы цен; в нашем SLA: budget
  `<5`, mid `[5,30)`, premium `[30,150)`, luxury `[150,∞)` EUR (полуинтервалы, минусовые
  цены и 0.0 относятся к budget — представлено как `(-inf, 5.0)`).
- **Новый vs возвращающийся (new vs returning)** — сессия «новая», если это первая сессия
  данного пользователя по времени (`session_number == 1`).
- **Описательный vs подтверждающий анализ (descriptive vs confirmatory)** — описательный
  показывает «что видно» без утверждений о значимости; подтверждающий (этапы 05–06)
  тестирует заранее зарегистрированные гипотезы.
- **Разрежённые сегменты (sparse segments)** — сегменты с малым объёмом; их конверсия
  ненадёжна (широкие CI, риск ошибки II рода) — luxury (42 438 сессий) под прицелом.
- **Факторизация воронки (`_funnel_from_flags`)** — общий внутренний расчёт шагов
  view→cart / cart→purchase / view→purchase; одна ветка кода используется и для общей
  воронки, и для сегментных — нельзя «слегка разойтись» формулами между ними.

## Что сделано

### 1. Сегментные метки (`src/segments.py::assign_segments`)

Добавляет ровно пять колонок, не трогая исходные: `price_tier` (одна exhaustive-цепочка
по `PRICE_TIERS`), `visit_kind`, `is_weekend` (dayofweek ∈ {5,6}), `daypart` (4 части суток),
`month_label` (год по правилу датасета: {10,11,12}→2019, {1,2}→2020, иное → ValueError).
Год выводится из месяца сессии (колонка `month`, без года в контракте) — правило
привязано к задокументированному охвату датасета.

Границы цен закреплены тестами: цепочка `when` перепроверяется против констант
`PRICE_TIERS` (кросс-пин, тест `test_tier_chain_stays_in_lockstep_with_constants`), так что
согласованное «вручную» изменение и констант, и цепочки всё равно ловится.

### 2. Одна воронка для всех (`_funnel_from_flags` + `segment_funnel`)

`funnel_rates` и `segment_funnel` разделили общий приватный расчёт `_funnel_from_flags`
(шаги по `_FUNNEL_STEPS`, те же числитель/знаменатель, тот же Wilson CI). Для `funnel_rates`
выход семантически байт-в-байт (тесты этапа 02 не менялись), для `segment_funnel` —
те же колонки + `segment:str` + `n_sessions:int`. `segment` всегда строка (даже для
булевого семейства `is_weekend`).

Ряды = (сегмент × 3 шага), сегменты отсортированы по метке. Пустой знаменатель в
сегменте — то же поведение, что у `funnel_rates` (исключение), а не тихий ноль.

### 4. Графики (`src/plots.py`)

- `plot_segment_rates(seg_rates, step, out_path)` — горизонтальные бары конверсии по
  сегментам с CI-усами, сортировка по конверсии, NA-сегмент рисуется если есть.
- `plot_price_conversion_curve(prices, out_path)` — как конверсия падает/растёт с медианной
  ценой сессии: децили цен (внутренне, x = медиана бина), обе ступени view→cart и
  cart→purchase с CI; null-цены явно исключены, пустые знаменатели — честный разрыв (NaN).

## Выводы (только описательные)

- **Прайс доминирует по объёму**, а не по сегментам-исключениям: half базу дают дешёвые
  сессии; luxury мал. Любые будущие тесты по прайсу примут форму «все пары ярусов против
  всех», и sparse-правило (n·p < 5 → не считаем z-тест) здесь пригодится.
- **Возвращающиеся сессии** вдвое превосходят новые по объёму — пространство для
  описательного сравнения воронок (не для вывода без pre-registration).
- **Сезонность**: равные по размеру месяцы, 2019-12 немного меньше — связывать с праздниками
  пока нельзя (это причинное чтение, статистика ≠ причинность).

## Подводные камни (pitfalls)

1. **Квантили vs фиксированные границы** — квантили «красивше делят», но не переиспользуются
   и не соответствуют бизнес-решению; платим за это размерами сегментов.
2. **Пустой знаменатель в сегменте** — если бы какой-то сегмент не имел ни одной
   `has_view`-сессии, `rate = num / den` бросил бы деление на ноль. Мы это не скрываем
   (такое же поведение у общей воронки) и записали в Raises-докстринг.
3. **Тип колонки `segment`** — булевое семейство (`is_weekend`) через `pl.lit` давало Boolean,
   а контракт обещает строку; исправлено принудительным `dtype=pl.Utf8` и запинено тестом
   для всех пяти семейств.
4. **Честность графиков — только что видно, без тестов это «видно» было бы не защищено** —
   дроп null-цен и разрыв при пустом знаменателе сначала были не запинены: тест «рендерится,
   файл непустой» не отличит честный разрыв от подклейки. Вопрос разбора: какое именно
   правило теста связывает картинку с правилом (x ниже порога null-цены, ровно один NaN).
5. **Sparse-сегмент = широкий CI** — не только мощность: точечная оценка конверсии luxury
   сама по себе ненадёжна. На этапе 05 практическая значимость должна требовать и объёма.
